# Identity Brokering Test

Console program that checks identity brokering: the identity provider types and builders, and the Admin REST API requests against a local HTTP server, offline; then, with a reachable Keycloak, identity provider management through the Admin REST API, the user manager on names that need encoding, the login redirect driven by `kc_idp_hint`, the password grant (revocation, offline token, `at+jwt` access tokens) and the `prompt=none` login.

SPID and CIE integration checks run only when the Keycloak extensions are installed (`spid-saml` from [italia/spid-keycloak-provider](https://github.com/italia/spid-keycloak-provider), `cieid-saml` from [lscorcia/keycloak-cieid-provider](https://github.com/lscorcia/keycloak-cieid-provider), same version line as Keycloak). No request leaves the Keycloak server (except the LinkedIn discovery document, read by Keycloak): Entra ID, Google, Facebook, Microsoft, LinkedIn, GitHub, GitLab, SPID and CIE are checked through the redirect Keycloak builds; the generic OIDC and SAML providers are bound to the master realm of the same Keycloak (discovery document and SAML descriptor imported through `localhost:8080` when Keycloak runs in a container), and only the redirect is checked. Keycloak itself imports the CIE pre-production metadata when it can reach the Internet (those checks are skipped otherwise), and the metadata of the CIE simulator from `CIE_SIMULATOR_METADATA_URL` (default `http://cie-simulator:8444/demo/metadata.xml`, skipped when Keycloak does not reach it).

## Test Keycloak (Docker)

`docker/` holds a throwaway Keycloak for this test, separate from the [sample environment](../../Docker/README.md) but built from the same image (`Docker/keycloak/Dockerfile`) and with the same spid-saml-check scripts (`Docker/spid-saml-check`): Keycloak 26.8.2 in dev mode (in-memory database `dev-mem`: nothing survives a restart; admin `admin`/`admin`) with the SPID 26.8.1 and CIE 26.8.1 extensions (built for Keycloak 26.8.x) (jars checked against their SHA-256), on `http://localhost:18080`, and the AgID SPID test suite [spid-saml-check](https://github.com/italia/spid-saml-check) 2.2.5, whose demo identity provider (`http://localhost:8443/demo`) makes a complete SPID login possible on this machine; a second instance on `http://localhost:8444/demo` stands in for CIE ID.

```bat
tests\IdentityProvider\docker\up.cmd     & rem build, start, wait until ready
tests\IdentityProvider\docker\down.cmd   & rem stop and remove
```

`up.cmd`/`down.cmd` use `docker` from the Windows PATH or, if missing, Docker inside WSL; `up.sh`/`down.sh` do the same on Linux/WSL. Variables: `KC_VERSION`, `SPID_VERSION`, `CIE_VERSION`, `SPID_SHA256`, `CIE_SHA256`, `KC_PORT`, `SPID_CHECK_VERSION`, `SPID_CHECK_PORT`, `CIE_CHECK_PORT`. The extensions are built for one Keycloak minor: keep the three versions on the same minor (e.g. Keycloak 26.7.x with the 26.7 extensions), with the SHA-256 of the two jars (shown by GitHub next to each release asset; the build fails on a mismatch). The ports are published on `127.0.0.1` only: the admin account is `admin`/`admin`.

The scripts of `Docker/identity-providers` (Entra ID, Microsoft, Google, Facebook, LinkedIn, GitHub, GitLab, OAuth 2.0, OpenID Connect: see [Docker/README.md](../../Docker/README.md#other-identity-providers)) also work on this Keycloak; run them after every start, the database is in memory:

```bat
powershell -ExecutionPolicy Bypass -File Docker\identity-providers\entra.ps1 -KeycloakUrl http://localhost:18080 -Realm iam4d-sample -AdminPassword admin
```

The redirect URI to register at the provider is then `http://localhost:18080/realms/iam4d-sample/broker/{alias}/endpoint`.

### SPID Test Identity Provider (spid-saml-check)

- The realm `iam4d-sample` includes the SPID provider `spid-test`, bound to the demo identity provider (entity ID `http://localhost:8443/demo`), with the mappers `fiscalNumber`, `email`, `name` and `familyName`; the realm user profile declares the attribute `fiscalNumber` (*Codice fiscale*, edited by admins only), otherwise Keycloak 26 drops it. Test users: `http://localhost:8443/demo/users`, e.g. `ada` / `password123` (SPID level 2).
- The demo identity provider signs with a key generated when its container is created (`spid-saml-check/entrypoint.sh`): the key of the image changes with its version and its certificate expires on 13 March 2027. At start spid-saml-check sets the new certificate on `spid-test` through the Admin REST API (`Docker/spid-saml-check/trust.js`, as `admin`) and registers the SPID SP metadata of the realm with the demo identity provider (`register.sh`); `up` returns when it is registered. A restart of Keycloak through Compose also restarts spid-saml-check (`depends_on` with `restart: true`), which registers the new realm again. A SPID provider bound to the demo identity provider and added later is rejected until the metadata is registered again: `docker compose exec spid-saml-check bash /iam4d/register.sh` in `docker/` (Docker in WSL: `wsl.exe --cd tests\IdentityProvider\docker -- docker compose exec spid-saml-check bash /iam4d/register.sh`).
- Keycloak publishes `http://localhost:18080` (`KC_HOSTNAME`) also to other containers: spid-saml-check downloads the SP metadata from `http://keycloak:8080` and gets the URLs the browser uses.
- `spid-test` can be deleted and saved again by the application, e.g. the *SPID* tab of the IdentityBrokering sample with the identity provider *SPID test (spid-saml-check)*, which imports the metadata from `http://spid-saml-check:8443/demo/metadata.xml` (signing certificate included). After the first registration `register.sh` keeps looking for a `spid-saml` provider every 5 seconds and registers the SPID SP metadata again whenever it changes; without SPID providers the metadata is not requested (Keycloak would answer 500).
- The image listens over HTTP but advertises `https://localhost:8443`: `Docker/spid-saml-check/entrypoint.sh` rewrites its server configuration and the demo entity ID for `http://localhost:SPID_CHECK_PORT`.
- The demo identity provider checks each AuthnRequest with spid-sp-test against the registered SP metadata, which must be valid: a `ServiceName` for the attribute consuming service (`WithAttributeConsumingService`) and a mapper for every attribute to receive. SPID identity providers send only the attributes requested in the SP metadata, which Keycloak derives from the mappers; `fiscalNumber` is the principal, without its mapper the login fails ("no principal in assertion").

### CIE Simulator (second spid-saml-check)

There is no official simulator of the CIE ID identity server, and its pre-production server accepts only federated service providers. `cie-simulator` is a second instance of the same demo identity provider on `http://localhost:8444/demo` (`CIE_CHECK_PORT`), relabelled *Simulatore CIE* (text only: no SPID, AgID or CIE logos). It answers like CIE ID (signed SAML response, `fiscalNumber`, `name`, `familyName`, levels `SpidL1` to `SpidL3`), but it is not CIE ID and does not check the CIE rules.

- The realm has no CIE provider: the application creates it, e.g. the *CIE ID* tab of the IdentityBrokering sample with the environment *Local test (CIE simulator)*, which imports the metadata from `http://cie-simulator:8444/demo/metadata.xml` (the Docker network name Keycloak reaches; the endpoints inside are browser URLs on `localhost`). The signing certificate comes with the imported metadata.
- `register.sh` looks for a `cieid-saml` provider in the realm `iam4d-sample` every 5 seconds (Admin REST API, as `admin`) and registers the CIE SP metadata of the realm with the simulator whenever it changes (e.g. new mappers): the login works a few seconds after saving the provider. Without CIE providers Keycloak answers 500 to `cieid-sp-metadata` and logs an error, so the metadata is not requested before. The container is healthy once the demo identity provider answers.
- Request checks off (`checkStrict` and `checkExtra` in `idp_demo.json`): the demo identity provider checks with the SPID profile of spid-sp-test, which CIE SP metadata does not follow.
- Users: the same as spid-saml-check. CIE ID authenticates at level 3, e.g. `marcopolo` / `password123`; any user with at least the requested level works. The login page gives up after 60 seconds (`loginTimeout`).
- CIE ID returns no email: the realm user profile requires one, so Keycloak asks for it at the first login.
- A restart of Keycloak discards the provider (in-memory database): save it again.

### End-to-End Login Check

`docker/e2e-login.py` signs in through the stack as a browser would, without Delphi or a browser (Python 3, standard library only): authorization code with PKCE for `iam4d-sample-app`, `kc_idp_hint` to the provider, login on the demo identity provider, signed SAML response back to Keycloak, first broker login, tokens. It prints every step and the id_token claims, exit code 0 when the login works. `docker/cie-provider.py create` saves the provider `cie` as the VCL sample does with *Local test (CIE simulator)* and waits for its SP metadata to be registered; `delete` removes it and the users the brokered logins created (username `tinit-...`), so the realm is back as imported. `KC_PORT` and `CIE_CHECK_PORT` as for the stack.

```
python docker\e2e-login.py spid-test ada password123
python docker\cie-provider.py create
python docker\e2e-login.py cie marcopolo password123
python docker\cie-provider.py delete
```

## The realm `iam4d-sample`

At every start the test Keycloak imports the realm `iam4d-sample` (`docker/realm/iam4d-sample-realm.json`), for the tests and the scripts above only: the samples use the realm `iamclient4d` of [`Docker/`](../../Docker/README.md). It has the public client `iam4d-sample-app` (PKCE, loopback redirect URIs), the confidential client `iam4d-sample-service` (secret `iam4d-test-only-secret`: test only, public, never reuse it) and the user `demo` / `demo` with `realm-admin`. Since Keycloak 26.8.2 an Admin REST API token also needs the audience of the `kc-admin-api` client scope, default only on `admin-cli` and `security-admin-console`: at start spid-saml-check adds it to the default scopes of `iam4d-sample-app` (`admin-api-scope.js`), and does nothing on older Keycloak.

The database is in memory: `down.cmd` (or a restart of Keycloak) discards what was created, the next start imports the realm again.

## Run

From a command prompt (RAD Studio 13, Win64 by default), with the test Keycloak running:

```bat
tests\IdentityProvider\run_tests.bat
tests\IdentityProvider\run_tests.bat Win32
tests\IdentityProvider\run_tests.bat Linux64
```

Variables: `KEYCLOAK_URL` (default `http://localhost:18080`; include the relative path if any, e.g. `/auth`), `KEYCLOAK_ADMIN` and `KEYCLOAK_ADMIN_PASSWORD` (master realm admin, default `admin`/`admin`), `CIE_SIMULATOR_METADATA_URL` (metadata of the CIE simulator as Keycloak reaches it), `RSVARS`. Without a reachable Keycloak the integration checks are skipped. The test creates and deletes the realm `iam4d-idp-test`.

`Linux64` runs through WSL: with the Docker Keycloak in the same WSL, `localhost` works; for a Keycloak running on Windows use the host address (`ip route` default gateway). Exit code: `0` all passed, `1` failed checks, `2` unexpected error. Build output goes to `tests/bin` and `tests/dcu`.
